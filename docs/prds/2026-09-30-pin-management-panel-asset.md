# 控制面板资产钉死并内置（PRD）

## Problem

运营者打开 `https://gemini.lab.sayweee.net/management.html` 登录时被拦下，页面提示「当前后端可使用 v0 管理接口，但不支持 v8。请将 CLIProxyAPI 升级至 v8 或更高版本后再使用此管理页面」。面板整体不可用，加账号、看日志、调配置全部做不了。

根因不在后端，而在于面板资产会**自动升级到一个我们不兼容的新契约**：

- `/management.html` 是从第三方仓库 `router-for-me/Cli-Proxy-API-Management-Center` 的 **latest release** 拉取、每约 3 小时按 SHA256 自动覆盖的外部资产（见 ADR 0003）。
- 该项目 **v1.25.0（2026-09-29）** 把 API 基址从 `/v0/management` 改成 `/v8/management`；探测不到 v8 时回探 `/v0/management/config`，探到就抛 `LegacyBackendError` —— 正是运营者看到的那句话。
- 我们这条 fork 分自上游 **v6.10.9**，只提供 `/v0/management`。上游已到 v8.0.4，其 v8 管理面是一套重新分组的 façade（`/credentials`、`/observability/*`、`/routing/*`、`/plugins/*`），其中配置端点吃的是 v8 新 YAML 配置树，属于大版本重构的核心。
- 已验证 **v1.24.2（2026-09-22）零处 `v8/management`**，是纯 v0 面板，也正是事故前 lab 上一直在用、能用的那一版。

问题的形状是：**一个第三方资产可以在我们毫不知情、也没有任何发布动作的情况下，把生产运营界面变砖**。修好这一次不够，得让它不能再自己发生。

## Solution

面板资产不再跟随 latest，改为**随我们的版本一起发布**：把 v1.24.2 的 `management.html` vendor 进仓库、`go:embed` 进二进制，默认路径上服务面板既不碰网络也不碰磁盘。

- 运营者打开 `/management.html` 拿到的永远是我们构建时选定的那一版，不会因为第三方发版而改变。
- lab 上那份已经落盘的 v1.25.0 不需要任何人工清理 —— 默认路径根本不再读磁盘，它自然失效。
- 面板版本从此是**构建期决定**的：升级面板 = 换文件 + 发版，是一次显式的、可评审的动作。
- 保留一个逃生舱：显式配置了面板仓库时，回到今天的「跟随该仓库 latest」行为，一行不改。
- 默认路径下后台自动更新器不再运行，不再每 3 小时下载一个没人读的 2.7MB 文件，GitHub API 403 限流噪音一并消失。

## User Stories

1. 作为运营者，我想打开 `/management.html` 就能正常登录并管理账号，这样我不必等一次发版才能恢复日常操作。
2. 作为运营者，我想面板不会在我不知情的时候自己升级成后端不支持的版本，这样运营界面不会一夜之间变砖。
3. 作为运营者，我想 pod 重建、镜像重拉之后面板依然是同一版，这样环境重建不会引入行为漂移。
4. 作为运营者，我想即使 lab 完全不能出网、或上游删掉了那个 release，面板依旧可用，这样面板可用性不依赖第三方仓库的存续。
5. 作为运营者，我想 lab 上已经落盘的那份坏面板不需要我进 pod 手工删除，这样修复只靠换镜像就能完成。
6. 作为运营者，我想 `disable-control-panel` 仍然能把面板整体关掉（含伴随页），这样关闭运营界面的语义不因本次改动而变弱。
7. 作为运营者，我想在确实需要试更新版面板时有一个显式开关切回「跟随 latest」，这样冻结不等于锁死。
8. 作为运营者，我想启动日志里能看到当前面板钉在哪个版本，这样排查「面板为什么是这个样子」时有据可查。
9. 作为运营者，我想不再看到每 3 小时一次的 GitHub 403 限流告警，这样日志里剩下的 warn 都是真问题。
10. 作为浏览器用户，我想重复打开面板时不用每次重传 2.7MB，这样页面打开依然快。
11. 作为开发者，我想有一条自动化断言保证内置面板说的是 `/v0/management` 而不是 `/v8/management`，这样将来误换成 v8 面板会在 CI 就被抓住，而不是在运营者的浏览器里。
12. 作为开发者，我想内置资产与记录在案的 sha256 始终一致，这样「我们到底发的是哪个文件」不靠人肉记忆。
13. 作为开发者，我想 `/usage-mode.html` 伴随页完全不受本次改动影响，这样已验证的运营能力不被牵连。

## Implementation decisions

### 面板服务：默认走内置资产

服务 `/management.html` 的处理器按**逃生舱是否配置**二选一：

- **逃生舱为空（默认）**：直接返回内置字节。不查磁盘、不发请求、不写文件。今天那条「文件缺失就同步下载」的按需兜底路径在此分支上完全不存在 —— 这点必须说破：那条路径**绕过了 `disable-auto-update-panel`**，只改后台定时器是修不好的。
- **逃生舱非空**：完全保留今天的行为（读磁盘，缺失则经资产更新器下载，含 GitHub API、digest 校验、fallback 页降级）。

`disable-control-panel` 的门禁位置不变，仍在两个分支之前 —— 面板关则一切皆 404，伴随页同步关闭（ADR 0003 的既有约定）。

### 逃生舱复用既有配置键，不新增

`remote-management.panel-github-repository` 非空即表示「我要跟这个仓库的 latest」。语义自洽，且省掉一个新键。文档需明确写出这层新含义：它现在不只是换源，而是**解钉**。

被否决的替代：新增 `panel-asset-url` / `panel-asset-sha256` 之类的运行时配置。理由是「面板版本」本质是「我们后端实现了哪套管理契约」的函数，属于开发决策而非运维旋钮；放代码里还让 lab 只需换镜像、不必改 k8s 里的 config。

### 为什么是内置而不是「钉死 URL 后照样下载」

先考虑过「钉死一个固定的 release 直链 + 内置 sha256 校验」。否决原因：换钉子照样要改常量、发版，**敏捷性一点没买到**，却留着一个只在最需要的时刻才失效的运行时依赖 —— 上游删旧 release、lab 出网被掐、pod 重建撞上下载失败，任何一条都会让 `/management.html` 直接 404（不是「面板旧了」，是「面板没了」）。同时该方案必须禁用 fallback 页（`cpamc.router-for.me` 永远是最新版，不堵住钉子会从这里漏掉），等于亲手拆掉最后一条退路。

内置之后，这一整类失效模式消失：构建期资产已在仓库里，构建不需要网；运行时不需要网。面板只可能因为**我们自己**换了个坏钉子而坏。

附带收益是设计本身大幅简化 —— hash 比对、原子写盘、digest 校验、fallback 分支、按需兜底下载，这些边界在默认路径上全部消失。

### 与 ADR 0003 的关系

ADR 0003 定的是「不 fork、不改外部面板，缺口用自建内嵌伴随页补」。本次**没有违反**：我们一个字节都不改它，只是把它随版本一起带走。但确实引入一条新约束需要记录：**面板版本从此是构建期决定的**。这对当下是好事（我们要的就是冻结），对将来是成本（升面板 = 换文件 + 发版），且随「迁移到上游 v8」完成而自动失效。

### 钉住的版本

`Cli-Proxy-API-Management-Center` v1.24.2，`management.html`，2,767,070 字节，sha256 `51b24db8170a5414875602c2f4e35017185b1c1dd7e9a6b1c0de69905a81e997`（下载实测与 release digest 双向一致）。sha256 以常量形式与资产一同入库，供自检断言使用。

### 条件请求

内置字节直接返回会丢掉 `c.File` 本来白送的条件请求语义，变成每次打开全量传 2.7MB。用标准库的静态内容服务 + 预设 `ETag`（取值就用上面那个 sha256 常量）拿回 304。

### 后台更新器的运行条件

抽一个纯谓词表达「后台面板更新器该不该跑」，下列任一成立即不跑：配置尚未就绪、`disable-control-panel`、`disable-auto-update-panel`、**逃生舱为空**。最后一条是本次新增。更新器的定时循环调用该谓词，其余逻辑不动。

### 仓库与二进制成本（实测）

资产 2,767,070 字节，gzip 后 884,642 字节。二进制涨 2.7MB（Go 原样嵌入，不压缩）；仓库涨约 880KB —— git 本就 zlib 压缩 blob，存原始文件与存 gzip 文件在仓库里体积相当，因此**存原始文件**，不引入解压逻辑。每次换钉子会再沉淀一个约 880KB 的 blob 在 git 历史里，但换钉子是罕见事件。

## Testing decisions

两个缝。主力在 handler 层，断言全部落在 HTTP 可观测行为上。

### 缝 A — `internal/api` handler 层（主力）

prior art：`internal/api/usage_mode_panel_test.go`（用 `gin.CreateTestContext` 直接驱动伴随页处理器，断言状态码 / Content-Type / body 里的真实管理端点引用）。本次照搬同一套做法驱动面板处理器：

1. 默认路径返回 200，Content-Type 为 HTML，body 即内置资产。
2. **body 含 `/v0/management` 且不含 `/v8/management`。** 这条直接把本次事故钉死：将来谁把内置资产换成 v8 面板，CI 就红，而不是等运营者的浏览器报错。
3. 响应带 `ETag`；带 `If-None-Match` 再请求返回 304 且无 body。
4. `disable-control-panel` 为真时返回 404（既有安全语义不回退）。
5. 逃生舱非空时改为吐磁盘文件而非内置资产 —— 用静态目录环境变量指向临时目录并预置一个可识别的文件，文件存在故不触网，测试无网络依赖。
6. 自检：内置字节的 sha256 等于随资产入库的常量。

### 缝 B — `internal/managementasset`（一个小表测试）

该包目前零测试。只测那个纯谓词：配置为 nil / 面板禁用 / 自动更新禁用 / **逃生舱为空** 四种情况返回 false，仅当逃生舱非空且其余门禁均放行时返回 true。纯函数、无 IO、无网络。

### 测试证明不了的那一件事

v1.24.2 面板对着我们这条 v6.10.9 血统的 v0 API 是否功能完好，只能由 lab 浏览器往返给出证据 —— 它在 2026-09-22 至 09-29 期间就是 lab 上跑着的那一版，这是最强的先验，但仍需运营者实跑确认（登录、账号列表、日志）。这是本需求唯一欠的人工验证，沿用上个 PRD 的同一模式。

## Out of scope

- **不在本 fork 上实现 `/v8/management` 门面。** 核心障碍是 v8 的配置端点吃的是 v8 新 YAML 配置树，与我们的 v6 配置结构对不上；即便硬接，面板设置页也是对着错误的树读写 —— 工作量不小却只换来一个半残的面板。
- **不在本需求里把 fork 迁移到上游 v8.0.4。** 那是独立项目：两个大版本 + 我们的自研特性（usage-mode、可用时间段、限流拦截阈值、伴随页、告警）重新落位。需要作为技术债记录，并附触发条件：上游 v8.0.4 **目前仍同时提供 `/v0/management`**，v0 契约没死，钉子是安全的；真正该启动迁移的信号是「我们需要 v1.25+ 面板的新能力」或「上游开始移除 v0 路由」。该债在 `req:learn` 阶段落入知识层。
- 不改 `/usage-mode.html` 伴随页的任何行为。
- 不改任何 `/v0/management/*` 端点的契约。
- 不提供运行时切换面板版本的能力（换版本 = 换文件 + 发版，这是刻意的）。
- 不做手工 `kubectl exec` 覆盖 pod 内资产的创可贴 —— 3 小时内会被定时器冲掉，换镜像才是终态。
