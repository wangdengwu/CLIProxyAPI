# 重新绑定时保留 auth 文件的运营者元数据 (PRD)

## Problem

运营者在 auth 文件里手工设置的字段，会在**重新绑定**（走完整 OAuth 登录）或**重新导入凭证**后被静默抹掉。

最初暴露这个问题的是 Claude 的 `claude_usage_mode`。该字段标记账号是共享（shared）还是独占（dedicated），独占账号不参与主动限流拦截。标记一丢，账号就退回默认的 shared 策略并可能被误拦 —— 2026-08-17 在 lab 实测到：一个本应 dedicated 的账号在 16:07:45 被 shared 动态阈值拦到 19:10，16:08–16:30 完全不接流量，同时还推了一条本不该发的企微告警。运营者只能事后手改文件补回标记，而下一次重新绑定又会丢。

但 `claude_usage_mode` 只是最先被发现的那一个。同一机制下被抹掉的还有 `priority`（账号优先级）、`note`（备注）、`headers`（自定义请求头）、`prefix`、`proxy_url`、`excluded_models`（按账号排除的模型）。这些全是运营者通过管理界面或手工设定的运营意图，日常改动都能正常持久化，唯独一重新绑定就集体消失 —— 行为不一致，且没有任何提示。

## Solution

重新绑定或重新导入凭证时，**新换来的凭证正常落地，运营者手设的字段原样留下**。运营者不需要在每次重新绑定后重新配置账号，也不需要记得哪些字段会丢。

唯一例外是停用标记：重新绑定一个已停用的账号视为要重新启用它，账号会回到可用状态。

行为边界对运营者可见且可预期：

- Claude、Gemini 账号重新绑定同一账号 → 字段保留（这是最初报告的场景）
- Codex 账号在订阅计划不变时重新绑定 → 字段保留
- Vertex 重复导入同一个 service account → 字段保留
- Kimi 每次登录都生成一个新账号条目，没有历史可继承 → 无保留行为，也无字段丢失

## User Stories

1. As a 运营者, I want 重新绑定 Claude 账号后 `claude_usage_mode` 的 dedicated 标记还在, so that 该账号不会退回 shared 策略被误拦。
2. As a 运营者, I want 重新绑定后账号的 `priority` 还在, so that 账号池的选择顺序不会被打乱。
3. As a 运营者, I want 重新绑定后账号的 `note` 备注还在, so that 我不用重新回忆这个账号是谁的、做什么用的。
4. As a 运营者, I want 重新绑定后账号的自定义请求头还在, so that 依赖特定头的账号不会在重绑后开始发错请求。
5. As a 运营者, I want 重新绑定后账号的 `proxy_url` 与 `prefix` 还在, so that 走特定出口或路由前缀的账号不会突然改走默认通道。
6. As a 运营者, I want 重新绑定后账号的 `excluded_models` 还在, so that 我特意排除的模型不会重新开始接流量。
7. As a 运营者, I want 重新绑定拿到的新 access token / refresh token / 过期时间确实是新的, so that 重绑真正解决了凭证失效问题 —— 绝不能出现"绑完却装回了旧凭证"。
8. As a 运营者, I want 重新绑定一个已停用的账号后它重新可用, so that 我不用在重绑之后再多一步手工启用。
9. As a 运营者, I want 首次绑定一个全新账号时行为完全照旧, so that 保留逻辑不给新增账号带来任何副作用。
10. As a 运营者, I want 即使某个 auth 文件内容已损坏，重新绑定仍能正常完成, so that 一个坏文件不会把我锁在"无法重新绑定"的状态里。
11. As a 运营者, I want 这个保留行为在文件、Postgres、对象存储、Git 四种后端上表现一致, so that 换存储后端不会改变账号配置的生死。
12. As a 运营者, I want 保留行为无需任何配置开关、默认就生效, so that 我不需要知道这个坑存在也不会踩到它。
13. As a 运营者, I want Kimi 登录的行为边界被明确写下来, so that 我不会误以为修复覆盖了它而做出错误预期。

## Implementation decisions

### 认知前提：两条保存分支

凭证保存存在两条互斥分支，这是整个问题的骨架：

- **元数据分支** —— 待保存的 auth 携带从文件加载来的完整元数据映射，不携带 token storage 对象。token 刷新（原地改写已加载的映射）、管理界面的字段修改、启停操作都走这条。写入是全量映射，**任何键都不会丢**。
- **storage 分支** —— 待保存的 auth 携带一个新构造的 token storage 对象。**只有登录与凭证导入走这条**（含管理界面与 CLI/SDK 两套入口，覆盖 Claude / Gemini / Codex / Kimi / Vertex）。落盘动作是截断重写，只写 storage 结构体的字段加上注入给它的元数据。

`priority` / `note` 等字段日常改动不丢、一重新绑定就丢，根因就是二者的不对称：**只有 storage 分支会丢，而只有登录与导入走 storage 分支**。

四个后端存储各自实现了近似拷贝的保存逻辑，其中**只有文件存储在 storage 分支上做了元数据注入**，Postgres、对象存储、Git 三份都漂移缺失 —— 生产/lab 实际运行的 Postgres 正是缺失的那条，所以即使调用方把元数据准备正确也会被丢弃。

### 组件：元数据保留 helper（新增）

与既有的「结构体 + 元数据合并」工具同包（该包已被 SDK 侧引用，同 module 内合法，无新增依赖方向）。

契约 —— 输入目标文件路径、待保存的 token storage、调用方准备的元数据映射，无返回值：

1. 算出**新载荷**：即落盘动作最终会写入的键集合（storage 结构体序列化结果与调用方元数据的合并）。
2. 读取目标路径的旧 JSON，取 `保留集 = 旧文件的键 − 新载荷的键 − 不保留名单`。
3. 把 `调用方元数据 ∪ 保留集` 注入给 token storage，随后由既有落盘动作写出。
4. 以下情形一律**静默 no-op**：文件不存在（首次绑定的正常情形）、文件为空、JSON 解析失败（记 debug 日志）、storage 不支持元数据注入。任何一种都不得让登录失败。

storage 类型的断言在 helper 内部完成，调用方不各自声明接口。

### 关键设计点：三层优先级由构造保证

优先级为 **旧文件保留键 < 新载荷字段 < 调用方元数据**。

这不是一条需要靠纪律维持的约定。既有的合并工具语义是「元数据覆盖结构体字段」，若把旧元数据整个带回来，旧的 access token / refresh token / 过期时间就会盖掉刚换来的新值 —— 重新绑定表面成功、实际装回死凭证。本设计规避它的方式是**保留集按定义排除了新载荷的每一个键**：冲突键根本进不了保留集，因此覆盖语义无从作用。

这个构造带来的直接结果是：**不保留名单只剩一个键**，无需维护一份易漂移的字段白名单。

### 不保留名单

只有**停用标记**一个键，对应"重新绑定视为重新启用"的决定：该键写不进新文件，auth 文件合成器读不到它便按可用处理。

凭证类与身份类字段（access token、refresh token、过期时间、上次刷新时间、邮箱、类型、id token、账号 ID、项目 ID）**因为都在新载荷里而自动落在保留集之外**，不需要单独列举。

旧 schema 遗留的历史垃圾键会被保留，这是可接受的：文件合成器忽略未知键，为它们维护一份名单的成本高于收益。

### 接入点

四个后端存储的 storage 分支各增加一次 helper 调用，位置在落盘动作之前。文件存储是把原有的注入替换为该调用（行为等价并额外获得保留能力），另外三个是新增。

**登录与导入的十个调用点一律不改** —— 它们传递的元数据本来就是正确的，问题出在存储层把它丢弃。

### 已知限制（写入设计，不视为缺陷）

保留以**文件路径为锚**：路径变了就没有旧文件可读，也就无从保留。

- Claude、Gemini —— 文件名由账号邮箱派生，重新绑定同一账号路径不变 → 保留生效
- Codex —— 文件名含订阅计划与账号 ID 摘要，计划变更会改变路径 → 计划不变时生效
- Vertex 导入 —— 文件名由 service account 派生，重复导入同一个 → 生效
- Kimi —— 文件名基于登录时间戳，每次登录必然是新文件 → **对 Kimi 是 no-op**。它同时也不丢任何东西（新条目本无历史），故不是缺陷，但不应指望本修复对 Kimi 产生效果。

### Accepted risk

Postgres、对象存储、Git 三个后端的保存逻辑**当前本就没有单元测试**（Git 侧现有测试只覆盖仓库准备逻辑；Postgres 与对象存储无测试文件且需要外部依赖）。这三处的接入正确性依赖「与文件存储逐字相同的一行调用」加 code review，**没有测试兜底 —— 包括生产与 lab 实际运行的 Postgres 这条**。

已评估并接受：为一行接线搭建三套新测试基建（起 Postgres 实例、造对象存储 fake）的成本高于其收益，而共享逻辑本身已被完整测试覆盖，可能漂移的表面仅剩「是否记得调用」这一行。

## Testing decisions

测试落在最高、最少的接缝上，验证外部行为而非实现细节。共两个接缝。

### 接缝 1（主）—— 保留 helper 的表驱动单元测试

helper 所在包目前没有测试文件，新建。用一个假 storage（实现落盘动作与元数据注入，只记录被注入了什么）直接断言注入结果，不触碰真实文件写出。

风格照现有 prior art：`sdk/auth/filestore_test.go` 的 `TestExtractAccessToken` 与限流特性的 `helps/ratelimit_*_test.go` —— 表驱动加 `t.Parallel()`，子测试逐例命名。

| # | 用例 | 断言 |
|---|------|------|
| 1 | 旧文件不存在 | no-op，注入内容等于调用方元数据原样 |
| 2 | 旧文件含 `claude_usage_mode` + `priority` + `note` | 三者都被带回 |
| 3 | **旧文件的凭证类字段与新值不同** | **一个都不带回** |
| 4 | 旧文件含停用标记 `true` | 不带回 |
| 5 | 旧文件为坏 JSON / 空文件 | no-op，不 panic、不返回错误 |
| 6 | 调用方元数据与旧文件同键冲突 | 调用方元数据赢 |
| 7 | storage 不支持元数据注入 | no-op，不 panic |

用例 3 是**凭证回滚回归护栏**，是这组测试里最重要的一条：它锁死"重新绑定后落盘的必须是新凭证"这个不可退让的行为（对应 User Story 7）。

### 接缝 2（接线）—— 文件存储的落盘验证

扩充文件存储现有的测试文件。在临时目录放一个含 dedicated 标记的旧 auth 文件，用真实的 Claude token storage（携带新凭证）走完整的保存路径，断言落盘 JSON 中凭证是新的、dedicated 标记仍在。

这条不可省：接缝 1 证明合并语义正确，但证明不了 helper 已被真正接进保存路径、注入的元数据确实流到了落盘动作。文件存储是四个后端里唯一既有测试文件又无外部依赖的，因此是接线验证的最低成本落点。

### 不覆盖的部分

Postgres、对象存储、Git 三个后端的保存逻辑不新增测试，理由与边界见上文 Accepted risk。

## Out of scope

- **不收敛四份重复的保存逻辑**：四者的错误信息前缀与后置步骤各不相同（Postgres 需 upsert 数据库记录、Git 需提交推送、对象存储需上传），合并是一次独立重构，风险与范围都远超本修复。
- **不改登录与导入的十个调用点**：它们传递的元数据本来正确。
- **不改 Kimi 的时间戳文件名策略**：不为了让保留生效而改动其命名，接受 no-op。
- **不加配置开关**：属 bug 修复，恒定生效。
- **不做重新绑定前备份旧 auth 文件**之类的兜底机制。
- **不给 `claude_usage_mode` 补管理界面支持**：目前管理接口的字段修改只认 `prefix` / `proxy_url` / `headers` / `priority` / `note`，设置该字段仍只能手工改文件。这是一个独立需求，建议单独开 ticket，本 PRD 不夹带。
- **不追认历史丢失**：本修复只保证未来的重新绑定不丢，不会去找回此前已被抹掉的字段。
