## What to build

任务 4 之后运营者能编辑窗口，但看着一串 `18:00-09:00` 仍然要自己心算"现在到底开着没有"——尤其跨午夜窗口，且窗口锚定的是服务端配置的时区，不是看页面的人所在的时区。

这一片让每一行直接显示**此刻开还是关**，关着的话显示**下次什么时候开门**。

**状态必须由服务端算好下发，前端绝不自己算。** 窗口锚定服务端配置时区，而浏览器时区是任意的——跨时区办公或浏览器时区异常时，前端自算会给出错误答案，而这个答案看起来完全合理，没人会发现。

## Key interfaces

- auth 列表接口的每个条目 — 新增三个字段：

  | 字段 | 含义 |
  |---|---|
  | 窗口原值 | 原样回吐，供输入框预填（任务 4 已需要）|
  | 此刻是否可用 | 布尔，服务端按配置时区判定 |
  | 下次开门时刻 | 带时区偏移的绝对时间戳；开门时省略 |

  下次开门时刻复用任务 3 那个计算实现，两处共用一份，不会漂移。

- 窗口为空、或全局开关关闭时 — 一律"此刻可用 = true"且省略下次开门时刻。这样页面会如实反映"功能被关了，谁都不受限"，而不是显示一堆其实不生效的"关门"。这是这两种情况必须显式覆盖的原因。

- 伴随页的窗口单元格 — 在任务 4 的输入框旁加一个开/关徽章；关门时一并显示下次开门时刻。渲染是纯展示逻辑：把服务端下发的三个字段转成徽章文案与时刻文本。

- 时刻的展示 — 服务端下发的是带时区偏移的绝对时间戳，页面展示时不要做任何时区换算的自作聪明，以免和服务端判定的"此刻开/关"自相矛盾（例如徽章说关、旁边的时刻却显示成一个已经过去的时间）。

## Known data variants

页面渲染必须扛住列表接口的这些取值组合：

- 窗口已配置且当前关门 → 有窗口原值、可用为 false、有下次开门时刻
- 窗口已配置且当前开门 → 有窗口原值、可用为 true、**无**下次开门时刻
- 窗口未配置 → 窗口原值为空或字段缺失、可用为 true、无下次开门时刻
- 全局开关关闭但账号配了窗口 → 有窗口原值、可用为 true、无下次开门时刻
- 账号 auth 文件被手改成非法窗口 → 有（非法的）窗口原值、可用为 true（运行时 fail-open）、无下次开门时刻
- 字段整体缺失（老版本服务端或非 Claude 账号）→ 不得渲染出 `undefined`／`NaN`／`Invalid Date`，退化为不显示徽章
- 下次开门时刻为 null 或无法解析 → 同上，退化为占位，不崩溃

最后两条是硬性要求：本仓库此前在配额展示上正是栽在"字段缺失渲染出 NaN 与 Invalid Date"这类问题上。

## Acceptance criteria

- [ ] 列表接口为每个条目返回窗口原值、此刻是否可用、下次开门时刻三个字段
- [ ] 判定按配置时区进行（在本地时区设为 UTC 的环境下验证）
- [ ] 窗口未配置的账号返回"可用 = true"且省略下次开门时刻
- [ ] 全局开关关闭时，所有账号返回"可用 = true"且省略下次开门时刻，即使它们配了窗口
- [ ] auth 文件里是非法窗口的账号返回"可用 = true"（与运行时 fail-open 一致）
- [ ] 下次开门时刻与任务 3 错误里的恢复时间来自同一实现，同一账号同一时刻两者一致
- [ ] 页面每行显示开/关徽章；关门行一并显示下次开门时刻
- [ ] 上述全部字段取值组合下页面均不出现 `undefined`／`NaN`／`Invalid Date`
- [ ] 字段整体缺失时页面退化为不显示徽章，且不影响该行其余内容与任务 4 的编辑功能
- [ ] 纯展示逻辑的断言从发布文件中**逐字抽取**后运行（抽取而非拷贝，避免漂移），覆盖上述全部组合
- [ ] 页面 HTTP smoke 可见徽章相关标记
- [ ] 在 lab 上完成一次浏览器确认：徽章与实际调度行为一致
