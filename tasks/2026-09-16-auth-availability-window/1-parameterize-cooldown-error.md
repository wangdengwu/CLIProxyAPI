## What to build

纯重构，无任何用户可见变化。**先让改动变容易，再做那个容易的改动。**

调度层现有一个"所有凭证都在冷却"的错误类型，它已经实现了一整套完整的 HTTP 错误渲染：`Error()` 返回一个 JSON 字符串（含错误码、人类可读消息、模型名、恢复时长的文本形式与秒数、可选的 provider），`StatusCode()` 返回 429，`Headers()` 返回带 `Retry-After` 的响应头。

后续任务 3 需要**第二种**语义不同但形状完全相同的错误——"所有账号都在可用时间段之外"。它同样是 429、同样要带恢复秒数与 `Retry-After`，只有错误码和消息文案不同。

把这套渲染参数化，让新增一种错误只需提供错误码与消息，而不是复制整套渲染逻辑。构造方式对调用方保持简洁：现有调用点不应因为这次重构而变得啰嗦。

**行为必须逐字节不变**：重构后，现有冷却错误产生的 JSON 字符串、HTTP 状态码、响应头集合，与重构前完全一致——包括字段顺序无关性之外的一切：错误码仍是原来那个、消息措辞一字不改、恢复时长的取整与"不足一秒显示为一秒"的处理、以及 provider 为空时该字段被省略的行为。

## Key interfaces

- 冷却错误类型 — 当前：错误码与消息在 `Error()` 内部硬编码。期望：错误码与消息由构造时决定，渲染逻辑共用一份。
- 冷却错误的构造函数 — 当前：接受模型、provider、恢复时长。期望：保持现有签名与行为不变（现有调用点零改动），另提供一条能指定错误码与消息的构造路径供任务 3 使用。
- `Error()` / `StatusCode()` / `Headers()` — 契约不变。`StatusCode()` 恒为 429；`Headers()` 恒含 `Retry-After` 与 JSON 的 `Content-Type`。

## Acceptance criteria

- [ ] 现有冷却错误的 `Error()` 输出与重构前逐字符相同（同样的错误码、同样的消息措辞、同样的字段集合）
- [ ] 现有冷却错误的 `StatusCode()` 仍返回 429
- [ ] 现有冷却错误的 `Headers()` 仍包含 `Retry-After`（秒数向上取整）与 JSON `Content-Type`
- [ ] provider 为空时，输出中不出现 provider 字段（与重构前一致）
- [ ] 恢复时长为 0、负数、以及不足一秒时的显示行为与重构前一致
- [ ] 存在一条可供任务 3 使用的构造路径，能产出相同形状但不同错误码与消息的错误
- [ ] 现有全部测试不加修改即通过
- [ ] 现有调用点无需改动

## Out of scope

- 不新增任何错误码或错误语义——那是任务 3 的事，本任务只铺路
- 不改变 429 这个状态码，也不改变响应头集合
- 不触碰调度过滤逻辑、候选收集逻辑，或任何 block reason
- 不改动错误在上层如何被转换成 HTTP 响应的链路
