## What to build

这一片端到端打通"账号只在指定时间段内参与调度"，入口是手工编辑 auth 文件（UI 在任务 4/5）。

运营者在某个账号的 auth 文件里写下 `available_window: "18:00-09:00"`，热加载后该账号只在北京时间 18:00 到次日 09:00 之间被调度器选中；其余时间对调度器完全不可见。不写这个字段的账号行为与今天完全一致（全天可用）。

配套新增一个顶层配置节，含两项：一个默认开启的全局开关，关掉它则所有窗口失效、全部账号回到全天可用；一个默认为 `Asia/Shanghai` 的时区，窗口的时刻以它为准。两项都参与既有的配置热加载。

**该能力刻意做成 provider 无关、usage-mode 无关**：任何账号配了窗口就生效，不去检查它是不是 Claude、是不是 shared。这让调度层不必承载 Claude 的业务语义。

**失败方向一律偏向放行。** 硬门禁的每一次误判都是静默摘号，所以运行时遇到任何拿不准的情况都放行：开关关闭放行、字段为空放行、字符串解析不了也放行（并打 warning 日志，让运营者有迹可循）。拦截写错的值是写入侧的责任（任务 4）。

## Key interfaces

- auth 文件顶层键 `available_window` — 字符串 `"HH:MM-HH:MM"`。缺失或空串表示全天可用。它属于 CONTEXT.md 里定义的 **Operator-set-keys** 家族，因此自动继承既有的跨登录保留机制（该机制按"旧文件顶层键减去新 payload 已定义的键"保留），无需登记任何白名单。
- 合成器的 auth 元数据读取 — 新增一段读取，形状与既有的 `claude_usage_mode` 读取一致：从 auth 文件元数据取出该键，trim 后非空则写入 `Attributes`。注意 `Attributes` 是 `map[string]string`，这也是该字段选用裸字符串形态的原因。
- `Auth` 上的窗口访问器 — 与既有的 `ClaudeUsageMode()` 同款契约：Attributes 优先、回落 Metadata、trim、空串表示未设置。
- 新配置节 `auth-availability` — 两个字段：布尔开关（缺省视为 true）与时区字符串（缺省及加载失败均回落 `Asia/Shanghai`）。**回落目标必须是上海而不是系统本地时区**：容器的本地时区通常是 UTC，回落到它会把 18:00 静默变成北京时间凌晨 2 点。
- 配置热加载 diff — 两个新字段都要能被检测到并记录变更，照既有 `default-usage-mode` 的 diff 写法。
- 包级配置快照 — 一个不可变结构，含"开关是否开启"与"已解析好的时区对象"，用 atomic 存取。在 Manager 设置运行时配置时写入。**时区字符串只在此处解析一次**：加载时区会读文件系统，绝不能放进每次选号的热路径。快照必须有非 nil 初值（开启 + 上海），否则配置尚未加载时会读到 nil。这与该包既有的全局注册模式同构（限流拦截正是靠一个包级 atomic 找到 Manager 的）。
- 调度过滤函数 — 当前签名接受账号、模型、当前时刻，返回"是否拦截、拦截原因、何时恢复"。期望：在 `Disabled` 检查**之后**、限流拦截检查**之前**插入窗口判定。位置理由：窗口不依赖任何运行时状态，最先短路最省事；放在 `Disabled` 之后是因为停用是更强的信号。
- 新的 block reason — 本任务只需引入这个原因值并从过滤函数返回；让它接上"带恢复时间的错误"是任务 3 的事。

**两条红线**：

- **绝不改动 `Disabled` 标志。** 后台 token 刷新只看 `Disabled`、不走调度过滤。用它实现关门会让账号整夜不刷新 token，开门时凭证已过期——功能会在最不该失败的时刻失败。
- **绝不改动限流拦截的持久状态。** 窗口是纯计算、无状态，改完下次选号立即生效，因此不需要 usage-mode 翻成 dedicated 时那种"清除拦截块"的配套动作。

## Known data variants

`available_window` 是运营者手写的字符串，必须扛住以下分布：

- 合法同日窗口 → `"09:00-18:00"`
- 合法跨午夜窗口 → `"18:00-09:00"`（本需求的主场景）
- 边界时刻语义 → **左闭右开**：窗口 `18:00-09:00` 在 18:00 整已开门、09:00 整已关门。与既有夜间判定的比较约定一致
- 字段完全缺失 → 全天可用（绝大多数存量账号）
- 空串 / 纯空白 → 全天可用
- 分隔符写错 → `"18:00~09:00"`、`"18:00—09:00"`（中文破折号）
- 格式写错 → `"6pm-9am"`、`"18-09"`、`"18:00"`（缺一半）、`"18:00-09:00-10:00"`、`"18:00:00-09:00:00"`（带秒）
- 数值越界 → `"25:00-09:00"`、`"18:60-09:00"`、`"-1:00-09:00"`、`"18:00-24:30"`
- 全角数字 → `"１８:００-０９:００"`（中文输入法），看着对但不是 ASCII 数字
- **`start == end`** → `"18:00-18:00"`，语义歧义（全天开？永不开？），判为非法、不猜测
- 时区配置写错 → `"Asia/Shangai"`（拼写错误）应回落上海而非 UTC

以上所有非法输入在运行时的可观察行为都必须是**不拦截**。

**以下三种写法必须判为合法**（实现期澄清）。它们的共同点是意图无歧义，而判为非法会 fail-open——运营者以为设了限制、实际账号全天在接流量，这比拒绝更危险：

- 宽松空白 → `" 18:00-09:00 "`、`"18:00 - 09:00"`、`" 18:00 -09:00"`。每一半各自 trim 后解析
- **`"18:00-24:00"`** → `24:00` 表示当日终点（1440 分钟）。这是"下午六点到午夜"最自然的写法；`"00:00-24:00"` 则等价于全天可用
- **不补零的小时** → `"9:00-18:00"`、`"8:00-9:30"`

## Acceptance criteria

- [ ] 账号配置同日窗口时，窗口内可被选中、窗口外被拦截
- [ ] 账号配置跨午夜窗口时，窗口内（含跨越午夜的那一段）可被选中、窗口外被拦截
- [ ] 边界时刻按左闭右开判定：起始时刻整点算开门，结束时刻整点算关门
- [ ] 字段缺失、空串、纯空白的账号永远不被窗口拦截
- [ ] 上述全部非法输入均**不拦截**，且产生 warning 日志
- [ ] 全局开关关闭时，即使配了合法窗口也完全不拦截
- [ ] 不配置 `auth-availability` 配置节时，行为等价于"开启 + 上海时区"——用调度行为验证默认值，而非断言配置结构体字段
- [ ] 时区配置为无效名称时回落上海，不回落系统本地时区
- [ ] 窗口判定使用配置时区，而非进程本地时区（在本地时区设为 UTC 的环境下验证）
- [ ] 窗口外被拦截时返回的原因是新增的那个 reason，不是既有的"其他"
- [ ] 账号被窗口拦截不影响其 `Disabled` 标志，也不影响后台 token 刷新的判定
- [ ] 配置热加载后新的开关与时区立即生效，无需重启
- [ ] 并发读配置快照与热加载写入在 race 检测下无数据竞争
- [ ] 重新绑定/重新登录账号后 `available_window` 仍在 auth 文件中
- [ ] 所有涉及时间的测试通过注入当前时刻驱动，不依赖真实时钟

## Out of scope

- 管理接口的写入与校验（任务 4）
- 列表接口的派生字段与页面展示（任务 5）
- 全部账号关门时的错误形态——本任务只需返回新的 block reason，把它接上"带恢复时间的错误"是任务 3
- 多段窗口、每账号独立时区、按星期几区分
- 窗口关门时掐断进行中的请求：判定只发生在选号时刻，已选中的请求跑完为止
- 不改动既有的限流拦截逻辑、优先级分组逻辑
